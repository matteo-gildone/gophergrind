GopherGrind

> Gophers are born equal but they are not equal.

## What this is

A CLI game in Go, originally scoped as a Shakes & Fidget clone but evolved into its own thing: a permadeath coffee-break
roguelike. The design goal is specific — this is meant to give a developer a 2-5 minute mental reset when they're stuck
on a task or a bug. Every mechanic should be judged against that: does this help someone in a couple of minutes, or does
it ask more of them than that? There is no monetization, so there is deliberately no artificial scarcity (no capped
daily attempts, no engagement-farming timers) — the kind of thing live-service idle games use to drive retention has no
place here.

## Tech stack & conventions

- Go, standard library first. Minimal external dependencies.
- Cobra for the CLI subcommand tree.
- gostyl (github.com/matteo-gildone/gostyl) for terminal output styling — no TUI framework (no bubbletea etc.), plain
  text only.
- Module: `github.com/<you>/gophergrind`. Binary name: `ggrinder`.
- Stateless-per-invocation model: every command loads the save file, does one thing, persists, exits. No daemon, no
  long-running process, no polling. Time-gated mechanics (job cooldown, HP regen, shop restock)
  work by storing a timestamp and diffing it against wall-clock time on the next invocation.
- Prefer dependency injection for anything nondeterministic (see the RNG interface pattern in `internal/combat`) so game
  logic stays unit testable with fakes instead of real randomness.
- Prefer interfaces for resolution logic that's likely to get retuned (e.g. hit resolution, damage calculation) so
  formulas can be swapped without touching the surrounding loop — but don't pre-build this abstraction speculatively.
  Refactor into it when there's an actual second implementation to support, not before.
- All code and architecture decisions are owned by the developer, not generated by an agent. Agents working in this repo
  should review, critique, and help debug — not write implementation code unless explicitly asked to for a specific,
  scoped task.

## Architecture

```
cmd/ggrinder/ Cobra root command + subcommand wiring
internal/character/ character state, path tracking, leveling
internal/item/ equipment, potions
internal/combat/ fight resolution (pure, no I/O)
internal/dungeon/ monster tables, chained fights, rewards
internal/job/ safe income path, time-gated
internal/save/ JSON persistence, timer diffing
internal/shop/ daily-restock inventory, gold sink
internal/graveyard/ append-only log of retired hardcore characters
internal/ui/ output formatting via gostyl
```

## Design spec

### Character creation

A short (3-question) quiz, inspired by Kynseed, sets the character's starting stat distribution. Every character has a
fixed pool of 30 points split evenly (10/10/10) across Accuracy/Damage/Defence before the quiz redistributes it — the
quiz can push a character fully into one stat with zero elsewhere; the resulting early-game imbalance is an intentional
consequence of the player's choice, not something to soften. HP is a separate, fixed value untouched by the quiz. The
quiz sets starting stats only — it does not determine class/path (see Leveling & paths below). Player also chooses
hardcore (permadeath) or softcore at creation.

### Stats

Only four numbers exist on a character: **HP, Accuracy, Damage, Defence**. Every card, item, and effect in the game
should modify one of these directly — no derived-stat formulas, no translation layer.

### Combat

Opposed roll, not a fixed hit-chance threshold:

```
attackerRoll = rng() + Accuracy
defenderRoll = rng() + Defence
attacker hits if attackerRoll > defenderRoll
```

On a hit, Damage applies directly. Defence is pure evasion — it does not mitigate damage on hits that land, it only
affects whether the hit lands at all. Swing order is chosen randomly at the start of each fight; fighters then
alternate, and a round is a single attack. The fight ends when a combatant reaches 0 HP, or a cap of 10 rounds (10
swings) is reached — at which point the higher remaining HP percentage wins. On an exact HP% tie the defender wins;
because the player is always the attacker, the player loses draws.

See internal/combat/combat_test.go for the precise API contract. Randomness enters through an injected RNG interface (a
small subset of *rand.Rand), rolls are d20, and two rolls are consumed per swing (attacker then defender).

### Leveling & paths ("zero to hero")

- XP from dungeons and card offers on level-up, Vampire-Survivors style:
  each level presents a few cards, player picks one.
- **No respec.** Every choice is permanent — characters are like git branches with no reset. This applies to path
  selection too (see below).
- Levels 1-2: only universal cards (plain Accuracy/Damage/Defence/HP bumps), no path tagging. The character is
  narratively "nobody" at this stage, regardless of what the creation quiz set their stats to.
- From level 3 onward, path-tagged cards start appearing in the offer pool alongside universal ones. The moment a player
  picks a path-tagged card, that path locks in **permanently** — no crossing over to another path afterward, ever. A
  character's starting quiz lean and their eventual path are independent and can diverge (e.g. a full-Defence starting
  gopher can still become a Ranger).
- Three paths, one per combat stat:
- **Fighter** = Defence (the one who stands and takes it)
- **Ranger** = Accuracy (the one who doesn't miss)
- **Mage** = Damage (glass cannon — hits hard, no defensive investment)
- Path affects card *flavor only*, not mechanics. Implement this like localization: a card has a canonical ID and a
  fixed numeric effect: the display text is a separate lookup keyed by `(cardID, path)`, same pattern as a locale string
  table. Combat and leveling logic never branch on path — only display text does.
- Class/path unlocks which jobs are available (see Job below).
- Bonuses are flat values, not percentages, for v1 — percentages need a known baseline and a stacking rule (additive vs
  multiplicative) that can't be sensibly chosen before real playtesting data exists.

### Death & recovery

- **Hardcore**: 0 HP is permanent death. Character is retired to the graveyard — name, path, level reached, final stats,
  cause of death. Graveyard is flavor/history only for now, no mechanical effect on future runs.
- **Softcore**: 0 HP requires paying gold or using a potion to recover — not free. If the player has neither, HP
  passively regenerates 1 per hour as a guaranteed fallback until they're able to act again. This floor exists
  specifically so the tool never hard-locks the person it's supposed to be helping.

### Economy — two income paths

- **Job** (safe): time-gated real-world activity, started explicitly, pays flat gold on completion. Can be interrupted,
  but interrupting forfeits the reward. No combat risk. Which jobs are available depends on the character's locked path.
- **Dungeon** (risky): chained fights via `internal/combat`, rewards of gold, XP, loot, and a shot at leveling. This is
  where death/recovery triggers.
- **Shop**: restocks once per day, flat cadence, no scarcity logic beyond that. Gold sink for potions and equipment.
  Items grant Accuracy/Damage/ Defence/HP bonuses directly, same as cards.

## Testing

Table-driven tests with `t.Run`, per Go convention. Combat and any other nondeterministic logic should use an injected
fake RNG so fight outcomes are deterministic and scriptable. The combat suite will introduce the reference fakeRNG — a
scripted []int cursor implementing RNG — which later packages should follow.
